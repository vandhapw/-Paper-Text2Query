\begin{abstract}
Text2Query is a four-stage open-source pipeline that translates natural language questions about IoT sensor data into structured MongoDB queries, generates natural language answers, and optionally produces visualizations. The pipeline comprises: (S1) a decomposer that uses large language model (LLM) inference with regex fallback to parse questions into a structured QueryPlan; (S2) a query executor that translates the plan into MongoDB aggregation pipelines with time-aware filtering; (S3) an answer generator that produces natural language responses; and (S4) a visualization module that auto-generates context-appropriate charts. Evaluated on 205 benchmark questions spanning 10 operation types across three sensor collections, Text2Query achieves 100\% operation detection accuracy, 96.1\% collection identification, and 87.6\% field extraction (Jaccard similarity). The system handles statistical aggregation, anomaly detection, trend analysis, and cross-collection comparison---operations absent from existing text-to-SQL tools. Source code is available at \url{https://github.com/vandhapw/Text2Query}.
\end{abstract}

\section{Motivation}

IoT sensor deployments precipitate an unprecedented proliferation of multivariate time-series data, forming the backbone of smart building and environmental monitoring systems. However, the utility of this data is often bottlenecked by the technical expertise required for retrieval. Non-technical users---such as facility managers, environmental scientists, and building operators---face significant epistemic barriers in extracting actionable insights, as they typically lack the proficiency in proprietary database query languages required to interface with these systems.

The challenge is further compounded by the inherent complexity of IoT data, which necessitates specialized operations such as statistical aggregation over dynamic time ranges (\emph{DetectAverage}), population-level anomaly detection (\emph{DetectAnomaly}), and longitudinal trend analysis (\emph{DetectTrend}). Traditional database interfaces often fail to provide the intuitive flexibility needed to execute these complex operations, especially when queries span multiple collections with heterogeneous schemas.

To address these challenges, recent advancements have leveraged large language models (LLMs) and semantic parsing. Text-to-SQL systems, including Spider~\cite{yu2018spider}, DIN-SQL~\cite{pourreza2024dinsql}, and RAT-SQL~\cite{wang2020ratsql}, have significantly improved the mapping of natural language to relational queries. Similarly, LLMs based on the Transformer architecture~\cite{vaswani2017attention}---such as GPT-4~\cite{openai2023gpt4} and Qwen~\cite{bai2023qwen}---demonstrate a remarkable ability to synthesize code and queries from natural language. However, these technologies face three critical limitations in the IoT context: (1) a primary focus on SQL-based relational backends, leaving NoSQL time-series stores like MongoDB~\cite{mongodb} under-supported; (2) a susceptibility to hallucinations, where LLMs produce syntactically correct but semantically invalid queries; and (3) a lack of deterministic fallbacks, which is unacceptable in production environments requiring high reliability. While monitoring tools like Grafana~\cite{grafana} provide visual access, they still require manual query construction, maintaining the barrier to entry for non-technical users.

Text2Query mitigates this systemic deficiency by introducing a four-stage pipeline anchored by a \emph{QueryPlan} intermediate representation (IR). This proposed solution decouples semantic intent (what the user means) from execution intent (how to query MongoDB), enabling a robust hybrid processing strategy: a high-capacity LLM for complex parsing, a self-repair module for structural correction, and a deterministic regex-based fallback for guaranteed availability. Evaluated on a 205-question benchmark, Text2Query achieves 100\% operation detection and 96.1\% collection identification, demonstrating that a structured IR-based approach can successfully bridge the gap between natural language and NoSQL time-series querying.

\section{Software description}

\subsection{Software architecture}

Fig.~\ref{fig:architecture} shows the four-stage pipeline architecture. A natural language question enters S1 (Decomposer), which produces a structured \emph{QueryPlan} specifying the operation type, target MongoDB collections, requested fields, and time scope. S1 uses a hybrid approach: the primary path is an LLM (Qwen3.5:397B-cloud via Ollama) prompted with collection schemas and operation definitions; if the LLM output is malformed, a self-repair module corrects compound operations (e.g., \texttt{DetectOldest|DetectLatest} $\rightarrow$ \texttt{DetectRange}); if the LLM is entirely unavailable, a regex-based fallback parser uses keyword matching on curated alias tables covering English and Indonesian/Malay terms.

The QueryPlan IR is the central abstraction. Defined in \texttt{query\_plan.py}, it separates three concerns: (1) \texttt{SemanticIntent} captures what the user means (intent type, subject fields, time expression, confidence); (2) \texttt{ExecutionIntent} specifies how to query MongoDB (collections, fields, operation, Mongo filter, granularity, max buckets); and (3) \texttt{ValidationResult} tracks repair actions and confidence scoring. The \texttt{SCHEMA\_REGISTRY} enumerates three collections: \emph{plalion\_klaen\_sensor} (indoor, 10\,s sampling interval), \emph{plalion\_company\_sensor} (office, 5\,s sampling), and \emph{lighting\_weatherapi} (outdoor weather, 30\,min sampling), each with validated field lists.

S2 (Query Executor) translates the QueryPlan into a MongoDB aggregation pipeline. It applies time-aware filtering by converting time type labels (\emph{today}, \emph{this\_week}, \emph{global}) into UTC datetime ranges via \texttt{\_resolve\_time()}, with a \texttt{REFERENCE\_DATE} environment variable for benchmark reproducibility. An execution-time safety net (\texttt{\_safety\_repair\_op()}) provides a last-resort repair for any invalid operations that escaped S1 validation. S3 (Answer Generator) passes the original question and retrieved data context to an LLM with a system prompt enforcing grounding in retrieved data, unit annotation (\textdegree C, \%, ppm, \textmu g/m\textsuperscript{3}), and source labeling (Klaen = indoor, Company = office, WeatherAPI = outdoor). S4 (Visualization) auto-detects chart type from the operation and renders via Plotly~\cite{plotly}, using a universal grid builder where each row corresponds to a field and all collections are overlaid with distinct colors and marker symbols.

\subsection{Software functionalities}

The system provides the following key functionalities: (1) hybrid LLM+regex parsing achieving 99\% LLM success rate with deterministic regex fallback for the remaining 1\%; (2) self-repair of malformed QueryPlans, triggered on only 0.98\% of queries; (3) time-aware MongoDB filtering supporting 10 time scopes (\emph{last\_hour}, \emph{today}, \emph{yesterday}, \emph{this\_week}, \emph{last\_week}, \emph{this\_month}, \emph{last\_24h}, \emph{last\_7d}, \emph{last\_30d}, \emph{global}); (4) cross-collection comparison queries that detect indoor-vs-outdoor intent from keywords and auto-expand the collection list; (5) automatic Plotly chart generation for trend (line), compare/average/max/min (grouped bar), anomaly (scatter), and count (horizontal bar) operations, with PNG export via Kaleido and HTML fallback; (6) an interactive REPL interface (\texttt{final\_chat.py}) with persistent database connections and per-stage latency tracking; (7) a 205-question benchmarking framework (\texttt{benchmark\_rigorous.py}) with stage-independent metrics and statistical confidence intervals; and (8) a 71-test unit suite (\texttt{test\_unit.py}) covering all pipeline stages; and (9) bilingual support for English and Indonesian/Malay sensor terminology through curated alias tables in \texttt{s1\_decomposer.py}.

\section{Performance evaluation}

We evaluate the computational efficiency and robustness of Text2Query on a 205-question benchmark spanning 10 operation types, 3 MongoDB collections, and 11 time scopes. Each pipeline stage is evaluated independently against dual-annotated ground truth.

\textbf{Overall results.} S1 achieves 100\% operation detection (95\% CI: [98.2\%, 100\%]), 96.1\% collection identification (95\% CI: [92.5\%, 98.0\%]), 96.1\% time scope accuracy, and 87.6\% field extraction (Jaccard similarity). S2 achieves a 63.9\% data hit rate, primarily limited by time-scoped queries referencing current dates against data seeded from 2025. Setting \texttt{REFERENCE\_DATE=2025-02-15} in the environment resolves this mismatch, bringing the hit rate to approximately 85--90\%. The LLM path succeeds on 99\% of queries (203/205); only 2 queries require regex fallback. The self-repair mechanism activates on 2 queries (0.98\%). Median end-to-end latency is 18.7\,s, dominated by cloud LLM inference in S1 ($\sim$44\,s).

Fig.~\ref{fig:performance} shows per-operation accuracy across all 11 categories. All 10 core operation types achieve 100\% operation detection. S1 field extraction (Jaccard) averages 87.6\%, with higher values on single-field queries and lower values on multi-field requests where the LLM occasionally includes semantically related but unrequested fields.

\section{Limitations}

Despite the system's effectiveness, several limitations persist. First, the S2 data hit rate (63.9\%) is primarily dominated by time-scope mismatch between present-day query dates and historical seeded data; while this is a configuration issue rather than a query generation defect, it affects the apparent success rate in static benchmark environments. Second, cloud LLM inference latency ($\sim$44\,s) remains the dominant end-to-end bottleneck, which may hinder real-time interactive performance. Third, current evaluation covers three MongoDB collections in the indoor air quality domain, meaning cross-domain generalization to other IoT sensor types remains a target for future work. Finally, the current evaluation is quantitative; a planned user study with 10--15 participants is required to provide qualitative validation of natural language interpretation quality.

\section{Impact}

Text2Query catalyzes novel investigative trajectories in natural language interfaces for time-series sensor databases, a domain underrepresented in current NLP research. Three architectural contributions possess high modularity and extensibility: (1) the QueryPlan intermediate representation, which decouples semantic intent from execution intent---allowing researchers to extend the 10-operation vocabulary or port the IR to other NoSQL backends such as Cassandra or TimescaleDB; (2) the hybrid LLM+regex parsing architecture with self-repair, which establishes a rigorous methodological paradigm for robust NL-to-structured-output pipelines where 99\% LLM success is hardened with a deterministic fallback; and (3) the stage-independent evaluation methodology with per-stage ground truth comparison, which establishes a reproducible benchmarking protocol for future NL-to-query systems targeting IoT data.

Compared to text-to-SQL systems~\cite{yu2018spider,pourreza2024dinsql}, Text2Query handles operations that cannot be expressed in a single SQL query, such as cross-collection comparison across collections with different schemas and statistical anomaly detection using population-level z-score thresholds. Compared to dashboard tools like Grafana~\cite{grafana}, Text2Query mitigates the technical barriers to data access by providing zero-code natural language interfaces. This allows non-technical users to ask ``Is the air quality safe right now?'' and receive both a quantitative answer and a visualization without requiring knowledge of MongoDB schemas or query syntax.

The modular four-stage architecture supports independent component replacement, permitting seamless integration into diverse NoSQL ecosystems. Sub-10\,ms S2 query latency enables real-time integration with building management systems for automated environmental control. The open-source release on GitHub under the MIT License enables community adoption across smart building management, indoor air quality monitoring~\cite{who2010iaq}, environmental compliance, and industrial IoT domains.

\section{Conclusions}

Text2Query is a four-stage open-source pipeline for querying IoT sensor data in natural language. It achieves 100\% operation detection, 96.1\% collection identification, and 87.6\% field extraction on 205 benchmark questions spanning 10 operation types across three sensor collections. The hybrid LLM+regex approach with self-repair provides both flexibility (99\% LLM success rate) and reliability (100\% pipeline success with deterministic fallback). The QueryPlan intermediate representation supports ten IoT-specific operations---including anomaly detection, trend analysis, and cross-collection comparison---that go beyond SQL's expressiveness.

Future work includes streaming sensor data ingestion for real-time querying, multi-modal input combining voice with text, predictive queries, and integration with building management systems for automated HVAC control based on natural language queries.
